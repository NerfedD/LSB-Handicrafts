# LSB Handicrafts QA, security, and accessibility audit

Audit date: 2026-09-21. Original scope: this workspace and local execution, as authorized by the user. No deployed URL or hosted test accounts were supplied. The original audit added diagnostics without changing application behavior. The user subsequently requested fixes; see the remediation follow-up below. Original findings and run results are retained as historical evidence.

## Remediation follow-up

- BUG-001: customer, supplier, product, and inventory updates now check server-maintained revisions. Edit forms retain the revision from when they opened, including across background refreshes. Conflicts preserve drafts and ask the user to refresh. Product retries retain the revision returned by the successful catalogue save; a changed stock record is rejected rather than overwritten.
- BUG-002: direct client activity-log writes are revoked. Database triggers record core business changes atomically using server time and authenticated actor identity. Sign-in uses a parameter-free server RPC with session deduplication. Existing historical entries are visibly marked unverified. Existing workshop commands continue to write their own server-generated summaries.
- BUG-003: dashboard-prefill tests select a product-specific Start batch action, avoiding the intentionally unprefilled generic action.
- BUG-004: history navigation now waits for the destination before going Back. Cold-route loading traces exceeded the default five-second assertion limit; the runner now uses a 15-second assertion budget and a 60-second multi-step test budget. Assertions remain enabled, with no automatic retries. The runner is pinned to one worker: `fullyParallel: false` only serialises within a file, so a second worker ran a second spec file against the same dev server and the suite's stubs and sign-in fixtures are not shared safely that way. Two workers failed 57 of 94 tests and took 7.7 minutes; one worker passes 94 of 94 in 3.4 minutes.

Deployment order: apply `supabase/migrations/20260921122520_qa_integrity_guards.sql` before deploying the updated client, then refresh existing browser tabs. The consolidated `supabase/schema.sql` includes the same migration. These changes have not been applied to a hosted database. Existing old clients do not carry the new revision predicates and should not remain open during rollout.

The local regression suite checks stale-save rejection, actual SQL revision increments, forged audit insert denial, update/delete denial, transactional audit rollback, session deduplication, blocked/anonymous denial, and migration reapplication. Supabase's separate `db advisors --local --type security` check was attempted but could not connect to a local Supabase instance on port 54322; PGlite validation is not a substitute for hosted deployment checks.

Baseline commit: `d8a7612029cd9fad8ec00e34a0e82afc21e6c0a7`. Execution environment: Windows/PowerShell, Node `v26.5.0`, npm `12.0.2`; Vite reported `8.2.2` and Vitest `3.2.7`. Browser engine was installed Microsoft Edge; exact browser version was not recorded. The phased checklist contains 94 cases.

## Target and evidence boundaries

LSB Handicrafts is an internal management application for products, inventory, customer orders, deliveries, raw materials, production, customers, suppliers, staff accounts, and activity records. The stack is React, Vite, Tailwind, Supabase Auth/Postgres/Edge Functions, and a documented Vercel deployment. Personas are anonymous, Admin, Manager, Sales Staff, Production Staff, and Delivery Staff. Include blocked/deleted staff and active authenticated accounts without a staff record as negative personas.

Local browser target: `http://localhost:5199`. Playwright uses installed Microsoft Edge and network-stubbed Supabase. PGlite runs isolated PostgreSQL logic. Neither proves hosted Auth configuration, actual REST grants, deployed migrations, Edge Function behavior, multi-connection contention, TLS, or production response headers. No P0 vulnerability was established. Passing tests are not a WCAG conformance certification or a complete security clearance.

Evidence labels used below:

- **Executed:** a command or assertion actually ran in this audit.
- **Reproduced diagnostic:** deliberately asserts an undesirable behavior to document a defect. A passing diagnostic means the defect exists.
- **Source-supported:** supported by inspected implementation, without an end-to-end exploit against a deployment.
- **Pending:** planned coverage, not claimed as completed.
- **Conditional:** execute if the relevant feature is enabled; otherwise record an explicit N/A with evidence.

Excluded from local execution: production database writes, live email delivery, real customer information, external provider internals, production stress testing, and hosted account lockout/rate-limit exhaustion. Use an isolated staging project for the server-bound cases below.

## Setup, fixtures, and execution protocol

1. Record commit ID, installed package versions, OS, browser versions, viewport, timezone, locale, database migration state, and test environment configuration. Record behavior-changing Auth settings without copying keys or tokens into reports.
2. Provision separate test users for all five roles, a blocked user, a deleted user with a previously valid session, and an Auth-only user without staff membership. Use two different actors for stale-edit tests.
3. Seed synthetic customers with unique names, duplicate names, Unicode names, missing optional details, and valid Philippine mobile numbers. Include suppliers with and without purchasing history.
4. Seed products with zero, low, sufficient, and reserved stock; packaged and custom-size lines; fractional prices; pending/completed/cancelled/partially delivered/refunded orders; deliveries at every stage; raw-material shortages and damaged receipts.
5. Use record counts 0, 1, page-size minus 1, page-size, page-size plus 1, and 1001+. Include long descriptions and names. Keep stable fixture IDs and known starting balances.
6. Run static checks and local unit/SQL tests, then browser happy paths, failure injection, keyboard checks, and the role/API matrix. Run real Auth/RLS/concurrency cases in disposable staging before making security release claims.
7. For every case record ID, status (pass/fail/blocked/N/A), role, preconditions, exact steps, expected result, actual result, evidence location, and cleanup result. Unexecuted checklist rows below are pending even if related coverage exists.
8. Compare before/after records from a fresh connection. A toast or a mock success alone is not proof of hosted persistence. Reset only identified synthetic records, respecting foreign keys; restore configuration changed by the test.

## Phase 6 — Performance, network, and edge scenarios

| Case | Procedure / diagnostic checklist | Acceptance criterion |
| :--- | :--- | :--- |
| NET-01 | Cold/warm load and key transitions under recorded Slow 3G profile and CPU throttling. | Measure navigation/interaction times, layout shifts, long tasks, and transfer sizes; compare to agreed budgets. |
| NET-02 | Offline before boot, after data loads, during edit, during save, and after server commits but before response. | Clear connectivity state, retained draft, finite wait, safe retry, and no duplicate stock/money effect. |
| NET-03 | Inject 400 on read/create/update/command. | Inline useful correction; no false success or repeated invalid request. |
| NET-04 | Inject 401 with expired refresh token on read/write and during session refresh. | Reauthentication path, protected-state cleanup, safe draft behavior, no infinite refresh loop. |
| NET-05 | Inject 403 and successful zero-row update caused by RLS. | Permission error; no optimistic success; no privilege workaround. |
| NET-06 | Inject 429 with numeric/date/missing Retry-After and repeated requests. | Bounded backoff, meaningful recovery, no retry storm; user cannot accidentally repeat committed work. |
| NET-07 | Inject 500, malformed JSON, empty response, HTML error page, connection reset, and timeout. | Recoverable error, retained input, no uncaught blank screen or leaked stack. |
| NET-08 | Delay/out-of-order read responses while saving, switching route, logging out, and changing account. | Old response cannot replace newer data or leak prior account data. |
| NET-09 | Simulate pagination failure on a later page and data changes between pages. | No partial data represented as a complete authoritative balance. |
| NET-10 | Inspect waterfall, asset dimensions/formats, compression, cache headers, redundant collection reloads, and main bundle. | Establish actual bottleneck before optimization; no sensitive response cached across users. |
| NET-11 | Loop navigation/dialog open-close/filter operations 100 times and sample settled heap/listeners. | No sustained retained growth after GC; no accumulating subscriptions or timers. |
| NET-12 | Storage disabled/quota exhausted, private browsing, corrupted persisted preferences and expired stored sessions. | Graceful recoverable startup and truthful persistence behavior. |
| NET-13 | Deploy new build while old tab remains open; load a lazy route and retry stale commands. | Safe refresh path; no schema/client incompatibility corruption. |
| NET-14 | Two real database connections interrupt transactions and retry after rollback/deadlock. | Atomicity, bounded lock wait, correct retry/idempotency; validate with PostgreSQL integration tests. |
| NET-15 | Inspect deployed HTTPS redirects, certificate, CSP, framing, referrer policy, and cache-control; check dependency advisories against lockfile. | Deployment-specific security controls verified. No current advisory scan or deployed header audit was performed here. |

Proposed measurement budgets to agree before release: LCP ≤2.5 seconds, INP ≤200ms, CLS ≤0.1 at the 75th percentile on the agreed real-user population. Treat local synthetic measurements separately from field percentiles. Set business API and recovery-time budgets from expected staff devices and connectivity; no performance compliance is claimed from bundle size alone.
